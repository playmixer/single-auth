# Single Auth
 
 **Single Auth** — это централизованная система управления учётными данными и правами доступа пользователей к различным приложениям. Сервис позволяет:

* централизованно управлять учётными данными пользователей;
* создавать и настраивать приложения для интеграции с сервисом;
* назначать роли и права доступа для каждого приложения;
* (future)контролировать и анализировать активность пользователей.

**Основные функции сервиса:**

* регистрация и аутентификация пользователей;
* управление учётными данными пользователей;
* создание и настройка приложений для интеграции с сервисом;
* назначение ролей и прав доступа для каждого приложения;
* (future)мониторинг активности пользователей;
* (future)формирование отчётов о действиях пользователей.

**Преимущества использования сервиса:**

* упрощение процесса управления учётными данными и правами доступа;
* повышение безопасности за счёт централизованного контроля доступа;
* снижение нагрузки на ИТ-отдел по вопросам управления учётными данными;
* улучшение пользовательского опыта благодаря единому интерфейсу для авторизации.

### Первый запуск 
- Создать администратора:
  - Подключить к контейнеру (зависит от ваших настроек)
    ```bash
    docker exec -it container-name-auth-server bash
    ```
  - Выполнить команду, указать имя пользователя и задать пароль
    ```bash
    ./manager -new -u admin -p password
    ```
- Авторизоваться на https://example.com/auth/login
- Админ панель на https://example.com/admin

### Описание глобальных переменных

- **LOG_LEVEL=debug**
  - **Тип:** строка
  - **Описание:** уровень логирования в системе. Возможные значения: `debug`, `info`, `warn`, `error`.

- **SERVER_BASEURL=https://example.com**
  - **Тип:** строка
  - **Описание:** базовый URL сервера, используемый для обращения к API.

- **SERVER_ADDRESS=0.0.0.0:8080**
  - **Тип:** строка
  - **Описание:** адрес сервера, на котором работает приложение.

- **AUTH_SECRET_KEY=secret_key**
  - **Тип:** строка
  - **Описание:** секретный ключ, используемый для аутентификации и шифрования данных.

- **JWT_ACCESS_TOKEN_TTL=3600**
  - **Тип:** целое число (в секундах)
  - **Описание:** время жизни JWT-токена доступа в секундах.

- **JWT_REFRESH_TOKEN_TTL=2592000**
  - **Тип:** целое число (в секундах)
  - **Описание:** время жизни JWT-токена обновления в секундах.

- **COOKIE_DOMAIN=example.com**
  - **Тип:** строка
  - **Описание:** домен, для которого устанавливаются куки.

- **COOKIE_SECURE=0**
  - **Тип:** целое число (0 или 1)
  - **Описание:** флаг, указывающий, должны ли куки быть безопасными (HTTPS). Значение 1 означает, что куки должны быть безопасными.

- **COOKIE_LIFETIME=0**
  - **Тип:** целое число (в секундах)
  - **Описание:** время жизни куки в секундах. Значение 0 означает, что куки будут удалены по закрытию браузера.

- **DATABASE_ADDRESS=postgres://root:root@localhost:5432/singleauth**
  - **Тип:** строка
  - **Описание:** строка подключения к базе данных PostgreSQL.

- **DB_PGS_NAME=singleauth**
  - **Тип:** строка
  - **Описание:** имя базы данных PostgreSQL.

- **DB_PGS_USERNAME=root**
  - **Тип:** строка
  - **Описание:** имя пользователя для подключения к базе данных PostgreSQL.

- **DB_PGS_PASSWORD=root**
  - **Тип:** строка
  - **Описание:** пароль пользователя для подключения к базе данных PostgreSQL.

- **REDIS_ADDRESS=localhost:6379**
  - **Тип:** строка
  - **Описание:** адрес сервера Redis.

- **REDIS_PASSWORD=vbrcth**
  - **Тип:** строка
  - **Описание:** пароль для подключения к серверу Redis.

- **REDIS_DB=0**
  - **Тип:** целое число
  - **Описание:** номер базы данных Redis.

- **REDIS_PORT=6379**
  - **Тип:** целое число
  - **Описание:** порт сервера Redis

## Архитектура и компоненты

Система состоит из следующих основных компонентов:

- **REST API** (на базе Gin) — предоставляет эндпоинты для аутентификации, управления пользователями и приложениями.
- **База данных PostgreSQL** — хранит пользователей, приложения, роли и сессии.
- **Redis** — используется для кэширования данных и хранения refresh-токенов.
- **Admin‑панель** — веб-интерфейс для администраторов, доступный по пути `/admin`.
- **Пользовательский интерфейс** — страницы входа (`/auth/login`), профиля (`/profile`) и другие.

## Детальный функционал

### Аутентификация и авторизация
- **Логин/пароль** — классическая аутентификация с проверкой хэша пароля.
- **JWT‑токены** — после успешного входа система выдаёт access‑токен (JWT) и refresh‑токен, которые хранятся в защищённых куках.
- **Refresh‑механизм** — позволяет обновлять access‑токен без повторного ввода пароля.
- **Выход (logout)** — инвалидирует refresh‑токен и очищает куки.

### Управление пользователями (админ‑панель)
- **Просмотр списка пользователей** — с поиском по логину.
- **Создание нового пользователя** — указание логина, email, пароля и флага администратора.
- **Редактирование пользователя** — смена email, пароля, прав администратора.
- **Удаление пользователя**.
- **Назначение ролей** — привязка пользователя к ролям конкретного приложения.

### Управление приложениями
- **Регистрация приложения** — каждое приложение получает уникальный `appID` (UUID).
- **Настройка ссылки авторизации** — URL, на который будет перенаправлен пользователь после успешной аутентификации.
- **Включение шифрования** — при необходимости параметры авторизации шифруются RSA‑ключами (генерируются автоматически).
- **Скачивание приватного ключа** — для расшифровки данных на стороне приложения.

### Роли и права
- **Создание ролей** — для каждого приложения можно определить набор ролей (например, `ADMIN`, `EDITOR`, `VIEWER`).
- **Назначение ролей пользователям** — администратор связывает пользователя с ролями в контексте определённого приложения.
- **Передача ролей в параметрах авторизации** — при переходе в приложение система передаёт список ролей пользователя в зашифрованном (или открытом) виде.

### Интеграция с внешними приложениями
1. Приложение направляет пользователя на `https://auth‑сервер/auth/login?appID=...&callback=...&state=...`.
2. Пользователь вводит учётные данные (если ещё не авторизован).
3. После успешной аутентификации система перенаправляет на `callback`‑URL, добавив в параметры `params` (зашифрованная строка с данными пользователя) и `state` (переданный из приложения).
4. Приложение расшифровывает `params` (если включено шифрование) и получает данные: `username`, `email`, `roles` и т.д.

| POST  | `/admin/users/:userID/remove` | Удаление пользователя |
| POST  | `/admin/users/:userID/upd` | Редактирование пользователя |
| POST  | `/admin/users/:userID/roles` | Обновление ролей пользователя |

## Инструкции по взаимодействию

### Для администраторов
1. **Первоначальная настройка**  
   После запуска системы создайте первого администратора с помощью утилиты `manager` (см. раздел «Первый запуск»).
2. **Вход в админ‑панель**  
   Откройте в браузере `https://ваш-домен/admin` и авторизуйтесь.
3. **Создание приложения**  
   - В разделе «Приложения» нажмите «Добавить приложение».
   - Укажите название и URL, на который будет перенаправлен пользователь после авторизации.
   - При необходимости включите шифрование (система сгенерирует RSA‑ключи).
   - Сохраните. Запишите `appID` — он понадобится для интеграции.
4. **Создание ролей**  
   - Перейдите в «Роли» для выбранного приложения.
   - Добавьте необходимые роли (например, `ADMIN`, `USER`).
5. **Добавление пользователей**  
   - В разделе «Пользователи» создайте учётные записи.
   - Назначьте пользователям роли в контексте нужного приложения.

### Для разработчиков интегрируемых приложений
1. **Получение `appID`**  
   Администратор должен предоставить вам идентификатор приложения.
2. **Настройка redirect‑URL**  
   Ваше приложение должно направлять пользователя на страницу входа Single Auth с параметрами:
   ```
   https://auth-сервер/auth/login?appID=<ваш_appID>&callback=<URL_вашего_приложения>&state=<произвольная_строка>
   ```
   Параметр `state` рекомендуется использовать для защиты от CSRF (например, хранить в сессии).
3. **Обработка callback**  
   После успешной авторизации Single Auth перенаправит пользователя на указанный `callback`‑URL, добавив параметры `params` и `state`.  
   Пример callback‑запроса:
   ```
   GET https://ваше-приложение/callback?params=eyJhbGciOiJSUzI1NiIs...&state=abc123
   ```
4. **Расшифровка параметров**  
   Если для приложения включено шифрование, параметр `params` представляет собой base64‑строку, зашифрованную RSA‑публичным ключом.  
   Используйте приватный ключ (скачанный из админ‑панели) для расшифровки.  
   После расшифровки вы получите JSON вида:
   ```json
   {
     "username": "ivan",
     "email": "ivan@example.com",
     "roles": "ADMIN,USER"
   }
   ```
   Если шифрование отключено, `params` — просто base64‑кодированный JSON.
5. **Авторизация в вашем приложении**  
   На основе полученных данных создайте сессию пользователя, проверьте роли и предоставьте соответствующий доступ.

### Для конечных пользователей
- **Вход** — перейдите по ссылке, предоставленной приложением, или откройте напрямую `https://auth-сервер/auth/login`.
- **Профиль** — после входа можно изменить пароль на странице `/profile`.
- **Выход** — кнопка «Выйти» доступна в интерфейсе профиля.

## Примеры использования

### Интеграция с веб-приложением на Node.js
```javascript
// Пример обработки callback
app.get('/auth/callback', (req, res) => {
  const { params, state } = req.query;
  // Проверяем state (защита от CSRF)
  if (state !== req.session.state) {
    return res.status(400).send('Invalid state');
  }
  // Декодируем params
  const decoded = Buffer.from(params, 'base64').toString('utf8');
  const userData = JSON.parse(decoded);
  // Создаём сессию
  req.session.user = userData;
  res.redirect('/dashboard');
});
```

### Запрос авторизации через curl (для тестирования API)
```bash
# Аутентификация
curl -X POST https://auth-сервер/api/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"password"}'

# Получение параметров для приложения
curl -X GET "https://auth-сервер/api/user/authinfo?appID=ваш_appID" \
  -H "Cookie: jwt=..."
```

## Дополнительные замечания
- Все чувствительные данные (пароли, секретные ключи) должны храниться в переменных окружения.
- Рекомендуется использовать HTTPS в production.
- Регулярно обновляйте приватные ключи шифрования (через админ‑панель).
- Система поддерживает горизонтальное масштабирование за счёт внешних Redis и PostgreSQL.
